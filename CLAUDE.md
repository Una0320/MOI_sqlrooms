# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A high-performance city-mobility trajectory visualizer built on **SQLRooms + Deck.gl + DuckDB-WASM**. It renders 20,000+ Agent-Based Modeling (ABM) trajectories from Parquet entirely in the browser, using zero-copy Arrow → GPU rendering and in-browser SQL aggregation. Originally derived from the official SQLRooms `deckgl-example`; now extended into a **civil-protection scenario viewer** with two top-level scenario types (shelter-in-place / mass-evacuation), each with its own trajectory data, OD arcs, and scenario-specific overlay layers (transit stations/waiting crowds vs. shelters/capacity).

## Commands

```bash
yarn install      # install deps (yarn is the lockfile of record; package-lock.json also present)
yarn dev          # Vite dev server
yarn build        # tsc -b && vite build
yarn lint         # eslint .
yarn preview      # preview production build
```

There is no test suite. `.env` needs `VITE_DUCKDB_CONNECTION_STRING` (base URL of a local HTTP server that supports **Range Requests**, default `http://localhost:7780`) — every actual filename is resolved from `src/constants/data.ts`'s manifest via `resolveFiles({scenario, control, ratio})` (see below), not from individual `.env` vars anymore. `VITE_MAPTILER_API_KEY` is optional: set it to make the default ("current") basemap MapTiler's `dataviz-dark` (rebuilt weekly) instead of CARTO's `dark-matter-gl-style` (OSM data rebuilt as infrequently as once a year per CARTO's own docs) — get a free key at cloud.maptiler.com/account/keys. Missing the key just falls back to CARTO with a console warning, it doesn't break local dev. All basemap config lives in `src/constants/basemap.ts` (see "Basemap" below).

### Local test data (`sim_data/`)

Local development points at whichever single delivery folder currently exists under `sim_data/` — folder naming varies per delivery (not always a date; currently `sim_data/20260916/`) — a delivered test batch (git-ignored, ask for a fresh copy if missing) with its own `README.md` describing 5 subfolders (`01_trajectory`, `02_points`, `03_stop_counts`, `04_shelter_capacity`, `05_moi_sim`) across 6 scenarios (`pt10/20/40`, `evac_ratio10/20/40`). This app currently only wires up **`05_moi_sim`** (trips + OD arc — schema-compatible drop-in for the existing `paths/timestamps/modes` query, so no query changes needed), **`02_points`** (bus stops/metro stations — only used as the coordinate join for Stop Counts; `shelters.csv` is currently unused), **`03_stop_counts`**, and **`04_shelter_capacity`**, selected by scenario × ratio (`pt10/20/40` for 大規模撤離, `evac_ratio10/20/40` for 就近避難 — see the manifest in `src/constants/data.ts`), plus `05_moi_sim/road_service_pt20.geojson` (road V/C service level; only that one file exists). `01_trajectory` (per-mode split files) is **not** wired up yet.

Since `sim_data/` isn't served anywhere in production, local dev needs a standalone static file server with Range + CORS support pointed at it, e.g.:

```bash
npx http-server sim_data/<delivery-folder> -p 7780 --cors   # e.g. sim_data/20260916 — check what's actually on disk
```

`VITE_DUCKDB_CONNECTION_STRING` just needs to match that server's base URL.

## Architecture

### Scenario switching (shelter-in-place vs. mass-evacuation)

- `useMapStore` holds three independent selectors — `scenarioType: 'mass_evacuation' | 'mixed_shelter' | 'priority_evac' | 'nearest_shelter'` (default `'mass_evacuation'`), `ratio: 10 | 20 | 40` (default **20** — `road_service` only exists for pt20; the ratio UI is the `pt  10 | 20 | 40` segmented control in the Timeline header, see "Timebar" below) and `networkControl: boolean` (default `false`). `setScenarioType` / `setRatio` / `setNetworkControl` all reset `time`/`timeRange`/`isPlaying` to their defaults (time axes differ wildly: `pt*` ≈ 70h, `evac_ratio10` ≈ 1.5h, `evac_ratio40` ≈ 11.8h — leaving the playhead would silently show nothing). `networkControl` is deliberately **not** touched by `setScenarioType`, so the switch survives scenario changes; `setScenarioType` also falls back to the first available ratio if the current one has no data in the new scenario.
- `<ScenarioSwitcher />` (top-center) is the scenario UI: three tabs 大規模撤離 (`pt*`) / 混合避難 / 優先疏散 (`SCENARIO_ORDER` in `data.ts`). 就近避難 (`evac_ratio*`) is **not in the tabs** any more, but its `nearest_shelter` manifest entries and file paths are kept — add `'nearest_shelter'` back to `SCENARIO_ORDER` to bring it back (until then Shelter Capacity has no reachable data and is disabled everywhere). A tab is disabled (title 「資料尚未提供」) when no ratio has data under the current control setting. The ratio selector is **not** here — it lives in the Timeline header (`timebar/RatioSelector.tsx`). `<NetworkControlToggle />` (top of the right-hand stack) is the Network Control switch — currently always disabled (no control-version files delivered); it stays clickable once on so it can be turned off.
- `src/constants/data.ts` holds the **manifest** (`MANIFEST`, keyed `scenario|control|ratio`) and `resolveFiles(key): FileSet`; unknown keys return an all-`null` set. `FileSet` fields are each independently nullable — `dataUrl`, `odDataUrl`, `stopCountsUrl`, `shelterCapacityUrl`, `roadServiceUrl`, plus `evacuationRate` (`'people_weighted' | 'leg_count' | null`). Nothing assumes stop-counts and shelter-capacity are mutually exclusive; that's just what the current delivery contains (pt* has stop counts, evac_ratio* has shelter capacity; README §5 explains why). Currently populated: `mass_evacuation|none|{10,20,40}` (pt*; `roadServiceUrl` only for ratio 20 — `road_service_pt20.geojson` is the only one delivered) and `nearest_shelter|none|{10,20,40}` (evac_ratio*); everything else (混合避難, 優先疏散, all `network_control`) is all-`null`. Adding a delivery = adding manifest entries. Helpers: `isAvailable` (has `dataUrl`), `availableRatios`, `isScenarioAvailable`. Consumers never read the manifest directly — they use `hooks/useResolvedFiles.ts`, which resolves from the store (`MainView.tsx`, `timebar/TimeLine.tsx`, `useODArcLayer.ts`, `useStopCountsLayer.ts`, `useShelterCapacityLayer.ts`, `useRoadServiceLayer.ts`, `useEvacuationRate.ts`) and rebuild their query from it every render; `useSql` refetches when the query string changes. A `null` url makes the owning hook run a guaranteed-zero-row query instead of erroring; `MainView` shows 「此組合無資料」 instead of the map when `dataUrl` is `null`.
- Layer availability is driven purely by the manifest: each `LAYER_CONFIG` entry has `requires: keyof FileSet` (e.g. `SHELTER_CAPACITY` → `'shelterCapacityUrl'`, `STOP_COUNTS` → `'stopCountsUrl'`), and `LayerPanel.tsx` shows **every** panel layer, disabling (not hiding) those whose url is `null` with 「此組合無資料」 (the hint sits on its own line under the title). The hooks also gate on the url being non-null.

### Single DuckDB engine (SQLRooms connector)
All in-browser SQL goes through **one** DuckDB-WASM instance — the SQLRooms connector created in `src/store.ts` via `createWasmDuckDbConnector()`. It drives the app's data loads below; the RoomShell chrome that used to expose it directly (sidebar with a SQL Editor / Data panel / file-dropzone / command palette toggle) was removed from `src/room.tsx` — it's end-user-facing product now, not a debug dashboard. `DataPanel.tsx` and the `data` panel registration in `src/store.ts` are still there (unreachable, harmless) so the sidebar can be added back trivially if that tooling is needed again later.
- **Trajectory load** — `MainView.tsx` uses the SQLRooms `useSql({query})` hook (`SELECT paths, timestamps, modes FROM read_parquet('${dataUrl from useResolvedFiles()}')`); the resulting `data.arrowTable` is passed as a **prop** to `<MapView arrowTable=... />`, which in turn feeds it to the trips layer, `useHeatmapLayer`, and `usePointsLayer` (all three share the one query result — zero extra DuckDB round-trips).
- **Histogram** — `timebar/TimeLine.tsx` uses `useSql` for the time-bin aggregation query, also against the current scenario's `dataUrl`.
- **OD-arc load** — `hooks/useODArcLayer.ts` runs its own `useSql({query: 'SELECT * FROM read_parquet(odDataUrl)'})` against the scenario's OD parquet, since OD data has a different schema/granularity than the trip trajectories. Still the same connector, just a second query.
- **Stop Counts load** — `hooks/useStopCountsLayer.ts` runs one `useSql` query that joins `03_stop_counts` (per-stop, per-time-bucket waiting counts) against `bus_stops.csv`/`metro_stations.csv` (for coordinates) via `LEFT JOIN ... ON mode = 8/16`.
- **Shelter Capacity load** — `hooks/useShelterCapacityLayer.ts` runs one `useSql` query against `04_shelter_capacity` directly (X/Y/name/capacity are already baked into that table, no join needed).

`useSql` returns `{ data: { arrowTable, rows(), toArray() }, isLoading, error }` and handles connector-init timing. Remote `read_parquet('http://...')` works natively in duckdb-wasm via Range requests. (Historically there were three separate DuckDB instances + a `window.globalArrowTable` hack; that was consolidated — do not reintroduce it.)

### State management
- **SQLRooms RoomShell store** (`src/store.ts`, `useRoomStore`) — room layout/panels; `dataSources` intentionally empty (data is loaded on demand via `useSql`). Panels: `main` (the map view, the only one actually reachable from the UI) and `data` (`placement: 'sidebar'` — registered but currently unreachable since `src/room.tsx` no longer renders `<RoomShell.Sidebar>`). `src/room.tsx` also passes `tileClassName="p-0 bg-transparent"` to `<RoomShell.LayoutComposer>` to kill `@sqlrooms/layout`'s default per-tile `p-2 bg-secondary/10` padding/tint — otherwise the light-theme tint shows as a border around the map.
- **Zustand `useMapStore`** (`src/zustand/useMapStore.ts`) — all playback/UI state: `time`, `timeRange`, `displayTimeRange`, `viewTimeRange`, `isPlaying`, `timeScale`, `selectedModes`, `visibleLayers`, `scenarioType`, `ratio`, `networkControl` (see the comment block at the top of the file for what each time range means).
- The rAF playback loop in `MapView.tsx` reads/writes Zustand via `useMapStore.getState()` to dodge closure-stale-value traps. Components subscribe with `useShallow` + atomic selectors to avoid re-renders during playback.

### Layer registry & visibility
- `src/constants/layers.ts` centralizes layer identity: `LAYER_IDS` (`trips`/`road-service`/`heatmap`/`od-arc`/`stop-counts`/`shelter-capacity`), `LAYER_CONFIG` (id + title + `defaultVisible` + `requires`), and `INITIAL_VISIBLE_LAYERS` derived from it. **`LAYER_CONFIG` order is the Layers panel order** (not the draw order): Trips · Heatmap · OD Arc · Shelter Capacity · Road Service · Stop Counts. The static facility markers (Stations bus/metro dots, Shelters dots) were removed from the panel and their code deleted (`useFacilityPointsLayer.ts`, `LAYER_IDS.STATIONS/SHELTERS`, `FACILITY_*_COLOR`, the manifest's `busStopsUrl`/`metroStationsUrl`/`sheltersUrl`): nothing else used them — Stop Counts joins `bus_stops.csv`/`metro_stations.csv` itself via its own query, Shelter Capacity carries its own X/Y.
- `useMapStore.visibleLayers` (`Record<LayerId, boolean>`) + `toggleLayer(id)` hold the on/off state; each layer hook/section in `MapView.tsx` reads its own `visibleLayers[LAYER_IDS.X]` to decide whether to build/return the layer.
- `LayerPanel.tsx` renders the checkbox UI (top-right stack, 284px wide, with `NetworkControlToggle` and `ModeSelector`) driven by `LAYER_CONFIG`/`toggleLayer` — adding a layer to the panel means adding one entry to `LAYER_CONFIG`, no other UI change needed. Titles are `whitespace-nowrap` (the longest, "Shelter Capacity · 避難所飽和率", leaves ~10px of slack at 284px — widen the stack in `MainView.tsx` before adding a longer title). `ModeSelector.tsx` tints the WALK/CAR/BUS/RAIL labels from `AGENT_MODE_TRIP_COLORS`. Entries whose `requires` url is `null` for the current scenario/ratio/control are disabled and dimmed with 「此組合無資料」 rather than hidden (see "Scenario switching" above). Both checkbox lists (Mobility Modes, Layers) use `accent-white` — checked stays white, not the browser-default/cyan accent. `NetworkControlToggle` uses the shadcn `Switch` (`components/ui/switch.tsx`), not a checkbox.
- Trips and the per-agent scatter dots ("Points") are **one** user-facing layer, `LAYER_IDS.TRIPS` ("移動軌跡") — there is no separate Points id/checkbox anymore. They remain zoom-LOD-exclusive internally: `MapView.tsx` only builds the trips `TripsLayer` when `currentZoom <= ZOOM_THRESHOLD` (11, from `usePointsLayer.ts`), and `usePointsLayer` only builds the dots above it; both read `visibleLayers[LAYER_IDS.TRIPS]`. **Don't confuse the LOD dots (`usePointsLayer`, replaces trips when zoomed in) with `LAYER_IDS.STATIONS` (static bus/metro facility markers, unrelated layer, unrelated data source)** — the naming collision bit us once already.
- **Road Service** (`LAYER_IDS.ROAD_SERVICE`, `hooks/useRoadServiceLayer.ts`, visual encoding in `constants/roadService.ts`, legend `components/RoadServiceLegend.tsx`) — a `PathLayer` over `road_service_<scenario>.geojson` (static peak-hour values, ~10MB / 30k links), fetched with plain `fetch` (not DuckDB) only when the layer is first turned on, cached per URL. Pushed **first** in `MapView.tsx` so it sits beneath heatmap and everything else. Colour = `LOS` A–F from the single `LOS_HEX` constant in `constants/roadService.ts` (A #44C23A, B #1FB33B, C #DFD34E, D #DF9651, E #D15528, F #C22E00) — the legend swatches use it directly and the map's RGBA table `LOS_COLORS` is derived from it (uniform alpha 220), so the two can't drift apart; width = `sqrt(log_V/C / log10(2.2))` mapped to 1.5–8px (`log_V/C` is `log10(1+V/C)`, **not** `log10(V/C)` — that's the separate `log10_VC` column), scaled 0.6×–1.6× across the map's zoom range; links sorted by V/C so congested ones draw on top. In scenarios whose `roadServiceUrl` is `null`, `LayerPanel` shows the checkbox disabled with 「此組合無資料」. The legend (`RoadServiceLegend`) shows **no numbers**: title "ROAD SERVICE (LOS)" + subtitle 「道路服務水準」, then a continuous 10px-wide A–F colour bar (six segments touching, only the outer top/bottom corners rounded) in one CSS grid with the letter (bold) and the Chinese description (`LOS_DESCRIPTIONS`: A 自由車流 … F 強迫車流（交通阻塞）), so each segment's height follows its row's text height and wraps stay aligned. Fixed width `ROAD_SERVICE_LEGEND_WIDTH_PX` = 232px (the Timebar is pushed right by this, see below). Removed from the old legend: the V/C threshold column (≤0.50, 0.50–0.65 …), the line-width key (sample bars + `V/C 0.05/0.50/1.00/1.20`), the 「LOS (V/C)」 / 「線寬 ∝ √log(1+V/C)」 captions and the 「尖峰小時靜態值 · 來源模擬：pt20」 footer (so `useRoadServiceSource`, `LOS_LABELS`, `ROAD_WIDTH_SAMPLES`, `logVcOf` were deleted).
- The map's own zoom is clamped to `[MAP_MIN_ZOOM, MAP_MAX_ZOOM]` = `[10, 15]` (`constants/map.ts`, passed as `minZoom`/`maxZoom` props to react-map-gl's `<Map>`) — zooming further than 15 doesn't add resolution this dataset can use, and `useStopCountsLayer`'s clustering ceiling is derived from the same constant (see below), so changing `MAP_MAX_ZOOM` is the one place to touch if the zoom range ever needs to change.

### Rendering pipeline (zero-copy)
- `MapView.tsx` — MapLibre basemap + `MapboxOverlay` Deck.gl overlay; runs the `requestAnimationFrame` playback loop; composes layers in order road-service → heatmap → od-arc → points (LOD dots) → stop-counts → shelter-capacity → trips (later pushes draw on top). Also wires a single `getTooltip` callback into the overlay, branching on `info.layer.id` (`'stop-counts-layer'` / `'shelter-capacity-layer'`) to show a hover tooltip. The top-left box (`left-14`, so it doesn't cover MapLibre's zoom buttons at x≈10–39) shows Time (HH:MM:SS), Zoom and the **`Evac Rate`** line, all default white except the Evac Rate *value*, which is `#DF9651` (≈8.3:1 contrast on the dark basemap, ≈5.2:1 worst case over a light one). The map style comes from `BASEMAP_STYLE` (`constants/basemap.ts`). The left panel is framed like every floating panel (`PANEL_FRAME`). The bottom-left legend stack now lives in `MainView.tsx` (not here — see "Floating panel layout" below). Shelter Capacity's legend rows come from `SHELTER_STATUS_LEGEND` + `SHELTER_STATUS_COLORS` in `constants/map.ts` (same colour table as the layer).
- `src/components/custom_layer/arrowTripsLayer/ArrowTripsLayer.ts` — a `CompositeLayer` that reads Arrow `RecordBatch` buffers directly. It slices the underlying `Float32Array`/`Uint8Array` (`paths`, `timestamps`, `modes` columns) via `subarray` using the batch's `valueOffsets`, rebuilds `startIndices` (offset ÷ 2 for [x,y] pairs), and feeds typed-array `attributes` straight into a per-batch `TripsLayer` — no JSON parsing. `updateState` caches the recomputed indices.
- `hooks/usePointsLayer.ts` — builds a single `ScatterplotLayer` (all agents as GPU instance attributes) as the LOD replacement for trips once zoomed in past `ZOOM_THRESHOLD`. Caches the per-agent flattened path/timestamp/mode arrays in a `useRef` keyed on `arrowTable` identity, then re-fills `positions`/`colors` typed arrays every render by interpolating each agent's position at `time` (binary search over each agent's own timestamp array, not a linear scan) — avoids re-parsing the Arrow table every frame.
- `hooks/useHeatmapLayer.ts` — one `ArrowPathLayer` per selected mode (own color + GPU `filterCategories`), additive-blended for a heat-density look; shares the trips `arrowTable` (no second query) and is gated behind a 300ms-debounced `timeRange` (frozen while `isPlaying`) so scrubbing doesn't rebuild layers every frame.
- `hooks/useODArcLayer.ts` — builds one `ArrowODArcLayer` from its own OD parquet query (see above), filtered by `timeRange`/`selectedModes`.
- `hooks/useStopCountsLayer.ts` — station-level waiting-crowd bubbles with **zoom-adaptive clustering**. Two data quirks drove its design: (1) `bus_stops.csv` encodes one row per *route-stop pairing*, so a single physical stop pole commonly has several `stop_id`s at the identical coordinate (up to 16, in one measured case) — rows are first grouped by raw `stop_id`/mode, then re-grouped by rounded coordinate (`LOCATION_PRECISION` = 6 decimals) so one physical station renders as one bubble with its waiting counts summed, not several overlapping circles; (2) even after that, ~554 physical stations is too many bubbles to show at once at low zoom, so a `supercluster` spatial index (built once per mode, since bus/metro are kept in separate indices so a bubble's color stays meaningful) is queried per zoom level to merge/split bubbles — re-clustering only happens on zoom change, while the per-frame (time-dependent) work is just summing each *currently visible* cluster's live waiting values via the same binary-search step-lookup pattern as `usePointsLayer`. Renders a `ScatterplotLayer` (radius ∝ `sqrt(waiting)`) plus a `TextLayer` printing the exact summed count inside each circle — no additive/glow blending, it made dense areas unreadable.
  - ⚠ **Supercluster `maxZoom` gotcha**: querying `getClusters(bbox, zoom)` at `zoom === options.maxZoom` still returns the *clustered* tier — only `zoom > options.maxZoom` returns fully unclustered raw points (see `supercluster/index.js`'s `_limitZoom`: it builds a dedicated raw tree at `trees[maxZoom + 1]`). So the constructor's `maxZoom` must be set to **one less** than the highest zoom you'll ever query at (`CLUSTER_MAX_ZOOM = MAP_MAX_ZOOM - 1`), while the query-side clamp uses `MAP_MAX_ZOOM` itself. Getting this off-by-one backwards silently caps declustering — bubbles stop shrinking no matter how far you zoom in, and it looks like a broken/ignored zoom level rather than an off-by-one.
- `hooks/useShelterCapacityLayer.ts` — one `ScatterplotLayer`, colored by the `status` field (`SHELTER_STATUS_COLORS`: empty/low/medium/high/over) with radius scaled by `load_ratio`. Same forward-fill step-lookup as stop counts, no clustering (shelters are few enough not to need it).
- `arrowODArcLayer/` and `arrowPathLayer/` are **live** — used by `useODArcLayer`/`useHeatmapLayer` respectively, not WIP experiments. `arrowODArcLayer/geoFanceLayer/` (geofence-based OD filtering) is still unused/WIP.

### Mode filtering (GPU bitmask)
- Mobility modes (WALK/CAR/BUS/RAIL) map to bits `[1,2,8,16]` (`src/constants/map.ts`, `MOBILITY_MODE_BITS`; bit `4` is a reserved/unused slot, never present in the source data).
- `ModeSelector` toggles bits in `selectedModes`; `MapView` OR-reduces them into a single bitmask passed as `filterBitMask`.
- `ModeObjectPropsExtension` (`.../arrowTripsLayer/utils/extensions.ts`) is a Deck.gl `LayerExtension` that adds the per-vertex `mode_type` attribute and pushes the bitmask + `colorMap` as a shader uniform (`mode-shader-module.ts`), so show/hide happens in the WebGL shader.

- **Evac Rate** (`hooks/useEvacuationRate.ts`, shown in the top-left Time/Zoom/rate box in `MapView.tsx`, hover for the tooltip) — `rate(t) = Σ weight of rows whose last timestamp <= t / Σ weight × 100`. One `useSql` query per scenario pulls every row's `list_max(timestamps)` and a weight (sorted by arrival); the hook builds a cumulative-weight array and playback is a binary-search lookup, no per-frame query. Cumulative: ignores the time window and `selectedModes`. The basis comes from the manifest's `evacuationRate`: **`people_weighted`** (`evac_ratio*`; hover: 「人數口徑（car agent = 4 人，其餘 = 1 人），基於 05_moi_sim 的 10,000 列抽樣。」) — one row = one agent, weight = 4 if `modes` contains car(2) else 1 (a car agent = 4 people per the sim_data README); all 60,000 rows across the six 05_moi_sim files have a single uniform mode, so no agent mixes car and walk (a hypothetical mixed row would count 4); based on the 10,000-row 05 sample (evac40 is only 10,000 of 40,133 agents). **`leg_count`** (`pt*`) — weight 1 per row; `pt*` rows are legs (up to 12 per agent) and 05 has no `person_id`, so the number is by *leg*, **not** a strict per-person evacuation rate (hover: 「以移動段(leg)計，資料缺少 person_id，非嚴格的人員撤離率」). Every scenario uses the same on-screen label, exactly **`Evac Rate`** (capital E and R, one space) — fixed by the user; don't reword, re-case or resize it (`LABEL` in the hook). The display shows `…` while the query is loading and `—` only for combos with no data.

### Basemap (`src/constants/basemap.ts`)
- All basemap config is in `basemap.ts`; `MapView.tsx` only reads `BASEMAP_STYLE`. `DEFAULT_BASEMAP` is `'current'` and **stays that until the user picks another** (they asked to compare first).
- Dev-only URL param `?basemap=<name>` (works under `yarn dev` only; production builds ignore it): `current` (MapTiler `dataviz-dark` if `VITE_MAPTILER_API_KEY` is set, else CARTO `dark-matter-gl-style`), `dark` (CARTO `dark-matter-nolabels-gl-style`), `positron` (CARTO `positron-gl-style`), `nlsc` (國土測繪中心 EMAP raster tiles). The three CARTO style URLs were `curl`ed (HTTP 200, JSON) before being written in.
- `nlsc`: WMTS endpoint `https://wmts.nlsc.gov.tw/wmts`, layer `EMAP`, TileMatrixSet `GoogleMapsCompatible`; the tile URL is the `ResourceURL` template read from `GetCapabilities` (`.../wmts/EMAP/{Style}/{TileMatrixSet}/{TileMatrix}/{TileRow}/{TileCol}` → `default`, `GoogleMapsCompatible`, `{z}/{y}/{x}` — note y before x), `image/jpeg`, CORS `*`, tiles exist z10–z18 (`maxzoom: 18`). Attribution 「國土測繪中心」. Desaturated/darkened via raster paint (`raster-saturation -0.8`, `raster-brightness-max 0.45`, `raster-contrast 0.1`) over a `#1e1e24` background layer.
- **Load check (no screenshots — verify via DOM/resource timing/console, not images):** all four options load with no console errors (other than the missing `favicon.ico`). `current`: MapTiler style + tiles HTTP 200, ≤ ~270ms; `dark` / `positron`: CARTO style + vector tiles HTTP 200, ≤ ~150ms; `nlsc`: 31 raster tile requests, all HTTP 200, median ~180ms, max ~290ms. The attribution control shows the right credit for each (the nlsc one reads 「國土測繪中心」). Don't take screenshots to judge basemaps — the user compares them by switching `?basemap=` themselves.
- **Early visual impressions (from a one-off trial before screenshots were dropped; the user makes the final pick)** (pt20, Trips + Heatmap + OD Arc + Road Service all on, 1600×900, zoom 10.6; Heatmap's additive glow can't be told apart from OD/Trips with everything on, so it wasn't judged separately; zoomed-in views weren't checked):
  - `current` (MapTiler dataviz-dark): dark, muted labels. Trips (white/yellow), OD Arc (red/blue) and Road Service (green) are all clear; panel edges separate fine.
  - `dark` (CARTO no-labels): darkest, highest contrast — every layer pops the most. No place names at all, so orientation relies on coastline/rivers.
  - `positron`: **not suitable as is.** Trips are white/pale-yellow and the trips/heatmap layers are additively blended, so on a near-white map they vanish; red OD / blue walk / green roads stay visible. The dark panels separate from it very clearly (but the new 1px `white/15` border is invisible there; the dark fill does the work).
  - `nlsc`: mid-grey after desaturation, with dense zh-TW labels baked into the raster (cadastral/section numbers, contour labels) that can't be hidden and compete with thin road/trip lines; Trips/OD still readable, less contrast than the dark styles. Fine for Taiwan-specific detail, noisy as a default.
  - Recommendation recorded: keep `current`; use `dark` if place names aren't needed; don't use `positron`; `nlsc` only with lower `raster-brightness-max` / if local labels are wanted.

### Floating panel layout (`MainView.tsx`, `constants/layout.ts`)
- Every floating panel (right-hand stack, top-left info box, legends, Timebar card, scenario tabs) uses `PANEL_FRAME` = `rounded-lg border border-white/15 backdrop-blur-md` — a 1px translucent light edge + 12px backdrop blur + one corner radius — so panel edges stay separable from any basemap, dark or light. (Before: right panels/legends had an opaque `slate-700` border + 8px blur, the Timebar a `ring-1` with no border + 12px blur and 14px radius, the left box no border/no blur/4px radius.)
- The bottom-left legend stack and the Timebar share **one** bottom offset, `PANEL_BOTTOM_PX` (= 40: the MapLibre attribution's top edge is 34px from the bottom, plus 6px), so their bottom edges are aligned and the Timebar no longer overlaps the attribution. The Timebar wrapper is positioned with explicit `left`/`right` instead of centring: normally both equal `calc((100% - min(90%, 72rem)) / 2)` (the old centred 90%/max-6xl box); while any legend is visible, `left` becomes `max(that, PANEL_EDGE_PX + legendWidth + LEGEND_TIMELINE_GAP_PX)`, where `legendWidth` is measured by a `ResizeObserver` on the legend stack (0 when every legend is hidden → Timebar returns to its original place). `left` has a 150ms transition. ### Timebar
`src/components/timebar/` — `Timebar` (play/pause + the right-hand control group `RatioSelector` · Time window · Speed), `TimeLine` (dual-range slider: display window vs. active range), `AdjustTimeSpeedRatio` (Speed x30/60/120/240) and `AdjustTimeWindow` (Time window 15/30/60 min; its `Custom` display logic is kept, but with the white handles disabled the width can only come from the buttons, so `Custom` is never triggered), both built on `CollapsibleChoice` (collapsed = one button, click to expand the options, picking one collapses it). `RatioSelector` is a segmented control — a label on the left, then **always-visible** `10 | 20 | 40` buttons (selected one highlighted, no dropdown) — placed left of Time window. The label text comes from the manifest side in `data.ts` (`RATIO_LABELS[scenario]`; `'pt'` for 大規模撤離, `'evac_ratio'` for 就近避難, `null` = no label), not from the component. It deliberately has **no tooltip explaining what ratio/pt means** (pending the data side); the only hint is 「此組合無資料」 on a disabled (no-data) button. Clicking calls `setRatio`, which resets the time axis; default ratio is 20. Width check (DOM-measured, Road Service legend open): at 1600 / 1280 wide nothing wraps or overlaps; with Time window *and* Speed both expanded at 1280 the gap between the 「TIMELINE 時間」 label and the control group is only ~15px (it would collide below ~1265px wide — if that matters, collapse the other chooser when one opens). Default window is `DEFAULT_TIME_WINDOW_SEC` (15 min, in `useMapStore.ts`). The Mobility Modes / Layers panels each have a −/+ collapse toggle (local `useState`, not persisted). The whole Timebar card is ~103px tall (compacted from ~167px: `p-2` card, 28px play button, 32px histogram track with 40px handles, 11px axis labels) — if you change its height (or `PANEL_BOTTOM_PX`), update the `max-h-[calc(100vh-190px)]` on the right-hand stack in `MainView.tsx`. **The two white handles (window start/end) are disabled — commented out, not deleted** — so the window width is changed *only* by the Time window button (15/30/60). Why: two ways to resize at once is too complicated, and at the timeline start the white handles overlapped the grey ones. Disabled: the white-handle JSX, the width-resizing branch of `handlePointerMove` (`'start'`/`'end'`), and the `activeHandle` state + its `setActiveHandle` calls + the `useState` import (a long explanation comment sits above the JSX block in `TimeLine.tsx`). The window's start/end are still *drawn* as two thin white bars (visual only — `pointer-events-none`, 4px wide, 40px tall i.e. 4px taller than the track on each side, `slate-200` with a 1px dark outline, the thinned look of the old handles), on top of the window body (subtle grey fill + cyan side borders, `minWidth` 12px so a 15-minute window ≈1% of the track stays grabbable; cursor `grab`, pans the whole window — it cannot be stretched). The grey display-range handles at the very start/end are deliberately low-key: a 2px `slate-500/70` line exactly as tall as the track frame (`h-8`, no overhang), with the same 8px transparent hit area and the same drag logic as before. Untouched: dragging the window body (`'range'`), the grey display-range handles (`display-start`/`display-end` — at the timeline start one of them sits under the window's start bar, so the cursor there is still `col-resize`), the Time window button. **To restore:** uncomment the JSX block, the `handlePointerMove` block, the `activeHandle` state and the two `setActiveHandle` calls, and put `useState` back in the import — see the comment in `TimeLine.tsx`. The restored handles are the *thinned* version: 4px visual bar in a 12px transparent hit area (`w-3`, `cursor-col-resize`, inner bar `pointer-events-none`), `slate-200` at rest, white + glow on hover/drag (originally 8px wide with a 1px border). When restoring, delete the visual-only white bars (the `z-30` spans) so there aren't two sets. Uses shadcn/ui `Button`/`Card`.

## Conventions
- **`apache-arrow` is pinned to `17.0.0`** (exact, plus `resolutions`/`overrides` in `package.json`). Do NOT bump it. The SQLRooms packages pin `17.0.0` and `@duckdb/duckdb-wasm` requires `^17`; if a second arrow version (e.g. 21) gets hoisted, the SQLRooms connector's `new arrow.Table(batches)` receives RecordBatches built by a *different* arrow instance, the internal `instanceof RecordBatch` check fails, and the Table constructor recurses infinitely → `RangeError: Maximum call stack size exceeded` on every query. Keep one arrow version across the whole tree.
- **Time unit is seconds everywhere** (0–86400, though `evac_ratio*`/`pt*` scenario timestamps can exceed 86400 since the underlying sim runs up to 72h), in both Zustand and DuckDB queries. Do not mix in JS milliseconds (formatting helpers in `timebar/utils.ts` multiply by 1000 only for display).
- Path alias `@/` → `src/` (configured in `vite.config.ts` and tsconfig).
- shadcn/ui configured via `components.json` (style `radix-nova`, base color neutral); UI primitives in `src/components/ui/`.
- Much of the codebase has Traditional Chinese comments; match the surrounding language when editing existing files.
- Deploy target is Netlify (`netlify.toml`): `npm run build` → `dist`, with `CI=false` and increased Node heap.
- `sim_data/` is git-ignored (large delivered test batch, not part of the repo) — local dev depends on it existing on disk plus a standalone http-server pointed at it (see Commands above). Don't assume it's present in CI/build environments.
